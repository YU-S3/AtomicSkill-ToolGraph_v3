## 0. 最重要的区别

目前 main 仍是旧机制代码。本文所说“删除”主要指：**v3.1 新主线接上以后，从新的工作树和安装包中删除已被替换的旧实现**，不是声称这些文件在当前 HEAD 已全部无人调用。

不要先把旧目录删掉，再一边补 ImportError 一边重建旧依赖。也不要把所有旧代码复制到 `legacy/` 后继续随新包安装，那只是换位置，没有精简系统。

本次没有删除或修改用户仓库；完成的是文件级清单、静态导入分析和只读清理检查器。未执行“生产替换完成后的全链路测试”，因为新主线尚未实现。

## 1. 旧版保存方式固定：Git 历史，而不是常驻第二套生产系统

1. 在删除前保存旧 main 的固定 commit/tag，以及本地未提交但确需保留的改动。工作区非干净时，先列出差异，不自动提交不相关文件或秘密。
2. 旧 Ours、旧五操作 IR、旧实验入口、旧测试、旧配置均可在这个固定版本恢复。需要复盘时使用**另一个目录的独立 worktree/环境**。
3. 新 main 最终只安装新经验式主线和必要公共组件；不提供“新 profile 报错就静默回旧 System”的退路。
4. 第一份文档第15节的 legacy 分流只作为切换期兼容方式。切换完成后，旧 `AtomicSkillGraphSystem` 导出及 fallback 分支从新 main 去掉。历史执行仍在固定旧 worktree 完成。
5. **旧 run、Bank、Trace、prompt/response、usage、原始输出、锁文件的历史副本不删除、不迁移成功信用、不改 hash。** Git tag 本身不包含未跟踪的实验产物，这些仍需原样保存在外部实验目录。

这样既能真正减少新主线代码，也不破坏旧实验复现。

## 2. 分类与删除条件

| 分类 | 操作 | 何时可以做 |
|---|---|---|
| 替换后整文件退役 | 从新 main 删除旧文件；历史 tag 保留 | 新实现接通，所有仍保留的入口/测试不再依赖它 |
| 迁出公共功能后退役 | 先移出少量必要函数/类型，改调用方，再删除旧大文件 | 迁出的函数已有相应回归，旧协议不被带回 |
| 原文件缩减/改写 | 保留文件位置或公共 API，只删除已废弃逻辑 | 与 v3.1 接入同时做 |
| 保留 | 当前仍有真实用途，不按名字一刀切 | 可做普通局部清理，但不删必要功能 |
| 历史配置/脚本/文档归档 | 新 main 删除旧入口，历史版本保留；新 README 指向唯一规范 | 新 runner 和命令已存在 |

`cleanup_manifest.json` 是逐文件分类，不是自动删除脚本。列表中的路径只对应上述基线的旧内容；若同一路径后来已重写成新实现，要显式重分类，不能按旧路径名删除新代码。
