# SkillCompiler 核心机制精简重构实施文档 v3.1

日期：2026-10-04。修改基线：`YU-S3/AtomicSkill-ToolGraph_v3@597cfc8d02906055bb5f28fb96ce6afdea8e2fff`。

**性质：经源码接入审查和受控原型验证的实施规范；生产代码尚待实现，不是模型学习效果已经通过的报告。**

**v3.1不改变已批准的简化路线。** 本轮只把工厂分流、RPC、实测案例构造、状态/冻结、恢复、Provider与文件执行等原v3.0要求补成可编码合同。第15—22节是同一方案的接入细则，不重新引入witness、owner、形式效果或多层资格。与v3.0冲突处以本版为准，不再并行实施两个版本。

**实施顺序：先本文，再《02_六Benchmark适配实施文档_v3.1》。** 本文中的新路径、接口、配置名均是实施合同，不是假称当前仓库已存在。

## 0. 已确认的决策与本版优先级

用户已同意：A）结果导向的准备能力提取；B）允许 E2 裁剪、归并和部分动态图；C）准备完成后自动接续；D）机制修改与降低模型推理强度分开。用户进一步明确要求大幅减少复杂证据、验证、依赖确认，允许 Agent 生成后通过真实运行检验。

本版据此将主线改为：

```text
真实经验 → Agent 提出能力/程序/工作流
         → 最小结构与执行隔离检查
         → 在 Train 案例中实际尝试
         → 保存可复用版本
         → Planner 选择/实例化
         → 程序连续执行，必要时 Agent 补齐或修复计划
         → 独立 Benchmark 评分
```

**不是**继续把新 Agent 输出翻译为旧版完整证据合同，再过一次旧 Atomicizer、R0/R1、完整覆盖证明与多层资格链。也不是把旧校验器改成 `return True`。

以下旧要求在新主线中明确失效：完整因果 owner 证明、E1 手工填写 witness 引用、两份历史提议 exact 合同一致、固定全部 occurrence 时间顺序、历史同值自动形成 DataFlow、每层独立晋升/部署证书、程序每条路径的形式效果证明、P0 必须先证明完整 TaskContract。

保留 A/I/T/G 的职责区分；不保留四层重复的证明与晋升制度。旧文档与本文冲突时，**新主线以本文为准**。旧实验按旧版本保存，不将其状态重命名成新方法结果。

## 1. 修改依据：已观察到什么，不预先承诺什么

本轮备份：`SkillCompiler_v2_12train_6valid_audit.zip`。已有核查显示：

- 四份准备提议把 `keychain/remotecontrol/candle/egg` 等类别输入用于 `agent.holds`，却用具体对象作为输出与见证；拒绝不能通过把类别与实例模糊相等来解决。
- 强制准备区间有的包含取物之后的放置、第二次取物或处理动作，原拟议局部效果在该区间末尾已不成立。
- current `CompositeEdgeCandidateBuilder.build()` 根据历史值相等、类型兼容选择最近前驱；`CompositeBuilder.validate_and_build()` 强制复用全部 canonical occurrence 时间顺序。这不足以证明新任务上存在同样的语义依赖。
- 本轮 stored Composite 中出现无明确目的的连续导航；其 location 输出进入后续取物 source 或灯位置，导致运行时位置冲突。
- 新版资格链已经能够使部分 Candidate 参与执行，不宜再把所有问题归因于未晋升。
- 实际验证请求中，一次 P1 输入为 25,332 tokens。运行成本必须包括 native tool schema，不只比较正文长度。

上述是修改依据。**删掉检查不保证成功率不变，更不保证 token 自动降低。** 本版减少不必要的拒绝与协议负担，并以实际任务分数、程序启动和实际费用检验结果。执行完成、返回字典与任务正确必须继续分开记录。

## 2. 主执行链只保留这些检查

| 保留项 | 具体内容 | 发生位置 |
|---|---|---|
| 可解析接口 | JSON/函数入口可读，必要字段、普通类型、被引用的变量/节点存在 | 装载、提交或调用入口一次 |
| 可运行结构 | 无未定义结果引用；工作流无无界环；脚本可装载；依赖版本能找到 | 编译/装载一次 |
| 权限隔离 | 只能访问本题公开输入、授权工具与工作区；不能访问答案、模型密钥、其他任务状态 | 公共工具 broker 与沙箱 |
| 资源边界 | 时间、内存、工具调用与整题预算；终止后不继续执行 | 实际执行中 |
| 实际反馈与输出 | 接受/拒绝、异常、输出字段是否存在、资源句柄是否有效；可用时使用轻量局部结果检查 | 工具返回时 |
| 实验真实性 | 正式分数由评分器给出；Train/Val/Test 隔离；冻结库只读；重复实验不串状态 | 实验驱动层 |

普通无结果、不适用、参数暂缺、错误答案都不是系统崩溃。缺某个可选局部检查器不阻止 Adapter 接入。

**不保留“已检查过还逐层重新证明”**：例如同一个文件句柄由 broker 产生后，消费者只检查本题范围和句柄有效性，不再要求一串历史 witness、domain、owner 和原始 revision 证明。

## 3. 明确删除、降级、替换的内容

| 原内容 | 新主线处理 |
|---|---|
| `input_provenance_refs`、`effect_witness_refs`、`local_value_authority_refs`、复杂输出推导证书 | 从 Agent 的必填输入输出中删除；真实来源由运行器在日志中自动关联 |
| 严格 owner/span lineage 才能提出能力 | 不再作为候选生成门槛；失败、回滚和成功片段可以作为经验，但必须保留其真实标签 |
| 强制最长完整准备区间 | 删除；以局部目标组织示例，Agent 可选择、裁剪、概括，示例不再充当程序正确性证明 |
| generalization current/history 两套实例化后分别 Atomicize | 删除这条主线路径；生成一份新候选，再跑实际测试 |
| 任意两字段历史同值 → 自动生成硬 DataFlow | 删除；由 Planner/Learner 显式声明普通参数引用 |
| E2 必须照抄所有 occurrence 的时间顺序 | 删除；允许省略探索步骤、合并准备流程、使用动态缺口 |
| 全局不可改的历史语义锚点 | 删除；本题计划可修订，用户原始要求和实际资源身份不因修订而被偷换 |
| Runtime 原子完成前必须逐层证明所有效果 | 删除；程序正常返回即可推进执行；可选局部检查失败时局部处理；最终正确性由独立评分判断 |
| 四层独立 Active、Preferred、发布证明和资格闭包 | 合并成程序版本的一份可用状态和实际尝试记录；A/I/G 不重复申请资格 |
| 语义/行为等价证明才能减少重复资产 | exact 内容哈希去重；相似候选用于检索，不自动迁移旧成功记录 |
| 每条程序路径的效果、历史循环同构证明 | 删除；可生成新的有界控制逻辑，靠沙箱、预算和 Train 实跑检验 |
| 所有 benchmark 必须提供 ALFWorld 式谓词本体 | 删除；普通文本、图像、文件与工具结果均可作为 I/O |
| 日志诊断格式限制导致 task failure | 非执行说明可截断展示，原始记录保留；不得修改动作参数或伪造结果 |
| 缺审计冗余字段就中止正常任务 | 降级为日志告警；真实评分、主要费用与执行错误仍需记录 |

这里删除的是主线依赖，不是把旧结果和源数据删掉。旧实现可以留在历史 tag 或独立 legacy 入口，不参与新运行。

## 4. 简化的数据模型：保留四层意义，不维持四套状态机

新增紧凑模型，不要求填充旧 `AbstractAtomicSkill.validator_spec` 等字段。

| 对象 | 必要内容 |
|---|---|
| Skill（A） | id、自然语言目标/说明、普通 input/output schema、简短 guidance |
| Implementation（I） | skill_id、program_id、必要的输入/输出字段映射；是调用关系，不单独晋升 |
| Program（T） | id/version、源码、入口、input/output schema、允许的工具接口、运行环境版本 |
| Workflow（G） | 目标模板、输入、节点列表、每节点目标/参数来源、明确顺序与最终输出引用 |

A 可以先有指导而没有程序。I 可以一对多；初版不实现语义等价迁移。G 是可实例化的策略模板，不是已证明必定完成任务的合同。

### 4.1 参数引用只保留四种

```json
{"task": "target_query"}
{"from": "find_target", "field": "object_id"}
{"literal": 2}
{"unresolved": "需要选择一个公开可达的位置"}
```

- `task`：本题公开输入或 Planner 对公开任务的解析结果；原始任务全文仍保留。
- `from`：前驱节点本次实际返回字段。不存在或尚未返回则等待/补齐，不伪造值。
- `literal`：程序常量或本次明确选择；不能填入私有答案。
- `unresolved`：明确把这个选择留给当前节点 Agent。

引用只表示参数传递，**不表示该值已被证明具有全部世界语义**。位置和对象关系可以由一个结果对象一起返回，避免代码因值相等自动建立关联。

### 4.2 一个节点的示例

```json
{
  "id": "take_target",
  "goal": "取得刚刚找到的目标对象",
  "skill_id": "take_object",
  "args": {
    "object_id": {"from": "find_target", "field": "object_id"},
    "source": {"from": "find_target", "field": "location"}
  },
  "after": ["find_target"]
}
```

`after`只表达计划顺序。删除旧 `REQUIRES_SKILL` 的逐谓词证明链；存在普通引用的节点天然依赖生产者完成。

## 5. 新程序统一采用普通受限 Python，不再要求模型填写证明型 Tool IR

这是本版明确的方法/资产格式变更：**新生成的程序默认使用 `sandbox_python_v1`；旧五-opcode IR 只保留旧实验回放与诊断兼容，不要求新程序先转换成旧 IR。**

原因是让 Agent 使用常规变量、分支、循环、列表和返回值，避免再填写 `expected_effects/path_expectations/evidence_outputs` 等复杂结构。同一程序接口可服务 ALFWorld 的多步交互、Spreadsheet 的代码处理和 OfficeQA 的检索/计算。

### 5.1 程序入口

```python
def run(ctx, inputs: dict) -> dict:
    # 只能通过授权公共接口观察/调用；不得调用 LLM。
    ...
    return {"status": "ok", "outputs": {...}}
```

合法 `status`：`ok / not_found / needs_input / blocked`。异常由执行器转成 `execution_error`。`ok`仅表示程序请求正常返回，**不是官方任务成功**。

### 5.2 `ctx`最小接口

```text
ctx.observe()                 最后一次真实公开观察/结构化公开结果，不额外改变环境
ctx.available_tools()         当前公共接口；枚举动作环境包含当前合法动作参数
ctx.call(name, arguments)     经 broker 执行一次授权原生操作，返回真实反馈
ctx.remaining_calls()         可用调用余额
```

读文件、写文件、检索等能力是 Adapter 注册的普通工具，不是 ctx 的私有万能权限。大输出使用工作区资源句柄，不全量塞入 LLM 上下文。

### 5.3 必须是真沙箱，不是删完验证后直接主进程 `exec`

生产执行器固定为容器边界中的Python worker，而不是把普通子进程称作安全沙箱。无Provider密钥、宿主根目录、Docker socket、答案或默认网络。交互通过stdin/stdout JSON RPC broker；只检查工具白名单、普通schema、资源范围和预算。具体生命周期见第17节。测试包中的本地subprocess仅允许运行手写fixture，不得接入模型生成代码。

- Python AST/编译检查用于尽早发现语法错误，不作为安全隔离保证。
- 第一阶段实现同一个worker的纯文本/原生环境RPC与可选工作区挂载能力。默认标准库；文件任务镜像预装依赖，第二阶段只选择依赖镜像与工具，不再重写后端。代码运行时不联网安装。
- `ctx.call`不能调用 Planner、Extractor、其他 LLM 或评分器；内部若发生 LLM 调用，该资产不属于此程序后端。
- 程序只返回字典，broker记录实际调用。脚本自报 `actions=100/success=true` 不写入计数或评分。
- 同一Program的语法/入口/声明检查在装载时做一次；每个具体调用只检查该次参数与资源。源码、接口、工具权限、ABI或镜像变化生成新版本，所有I/G引用固定版本，不用latest指针暗换程序。

### 5.4 ALFWorld桥接

脚本可以生成 `GO_TO/OPEN/TAKE/...` 的名称与参数。broker以**当前公开目录**作精确解析并执行；不可用则返回原生拒绝信息。无需脚本提供 revision witness 或证据链；broker内部仍处理当前动作ID失效问题。

可继续复用已有 public discovery 解析，把明确公开对象/位置提供为方便使用的普通数据；解析不出时保留原文，不将“缺形式化证明”当作对象不存在。禁止读取隐藏对象树来给程序提供目标位置。

不得预置手写 `find_and_take` 作为空 Bank 的 learned Tool。基础 Adapter 提供原生能力，搜索程序须由 Train 经验生成。

## 6. 学习链：候选先产生，运行再筛选

### 6.1 不再要求程序发明之前证明其历史完全成立

每题结束，运行器给 Learner：公开任务、实际动作/工具和反馈、最终评分摘要、已用程序、少量相关旧 Skill。失败事件保留失败标签，不伪装成成功。

Learner一次选择：

```text
no_change
reuse_existing
propose_skill_and_program_spec
propose_or_revise_workflow
```

每题最多提交一个需要新程序生成的候选。可以同时给出一份使用它的工作流草案。没有新能力时不调用 Builder；没有程序的指导仍可保存。

Learner负责概括语义目标和入口/出口，不负责证明所有历史动作。它可以从一个真实 Train 案例提出新循环或分支；第二个来源用于测试，不再是提议前必须满足的形式门槛。

### 6.2 示例片段只是材料，不是资格证书

运行器可以按节点边界、工具返回、发现对象或任务阶段组成短示例；当这些结构不可得时使用普通任务轨迹，不阻止该 Benchmark 学习。

Agent 可以裁剪探索过程、合并必要准备、重新安排非依赖步骤。原始 Trace不改变。source task/trace ID由运行器自动记录，模型不填写 witness、owner证明或一长串事件ID。

若模型对历史的解释有误，新程序可进入受控测试，但不能因此给历史记录补造成功事实。这里接受“程序是一个待测假设”，不是把它称为已经验证的历史抽取。

### 6.3 Builder的输出

输入：Skill目标、普通I/O schema、公开工具说明、至多两个相关Train示例、必要错误反馈。

输出：源码和一个普通调用示例。调用示例用于测试绑定，不是历史授权证明。

输入例如 `target_query="keychain"`，结果可以是 `object_id="keychain_1"`；不再要求模型写 `agent.holds($object)`。类别和实例的实际选择由代码执行与后续反馈检验，不做模糊身份合并。

首次生成一次，语法或实际执行错误最多修复一次；第二次仍失败就保留诊断，不循环追问。修复使用同一版简短协议，仅发送相关示例/代码/错误，不重发六万到十万token的全量历史。

### 6.4 重复资产

相同源码+入口+schema+允许工具集合+Adapter ABI+运行镜像hash直接复用；不同源码即使summary相同，也按新版本测试。相似目标只用于检索/提供旧方案，不要求大型语义等价证明；也不自动继承旧执行成绩。

## 7. 程序可用状态：一份状态，不再叠加四层资格

采用：`candidate / usable / disabled`。语法不通过的候选文件保留在诊断目录，不进入可调用注册表。

- **candidate**：可装载、权限声明合法；允许在Train或当前任务的显式受控试用中执行。
- **usable**：相同程序版本在两个不同物理Train任务上取得下面定义的正向实测记录（必须实际运行该程序版本，具体测试起点、入参与续跑方式见第18节）；允许普通选择和自动接续。
- **disabled**：已定位为程序本身失败，暂停该版本；修复后产生新版本。

**A没有额外晋升；I没有额外晋升；G没有额外逐边证书。** G作为策略模板先由Planner选择/实例化，实际调用遵循程序状态。没有usable程序的节点可走Agent，不阻止整个库冻结。

### 7.1 正向实测记录的唯一规则

候选必须实际启动、正常结束，输出满足普通schema，且不是其他程序或Agent代替它完成后冒领记录。结果依据分两类：

1. **有独立局部检查**：Adapter/固定测试例能检查该局部结果，记录 `local_check=passed`。它不是候选自己写的assert，也不是LLM自称完成。
2. **没有独立局部检查**：在完整Train任务中实际使用该程序输出，最终由独立Benchmark评分确认成功，记录 `basis=task_outcome`。此时只称“该版本在这个执行流程下通过任务测试”，不声称已证明局部语义或因果贡献。

只有shape正确、文件存在、返回`ok`，不能单独成为正向实测。对于只支持过程输出的程序，可正常试用；在无法取得上述两类结果时保持candidate/指导，不发明成功检查器。

对于连续分数，沿用该Benchmark已经定义的hard成功规则；没有hard规则时，在Adapter配置中显式声明用于程序测试的通过规则，否则仅保留分数、不做自动正向计数。

### 7.2 两个任务不需要额外复杂来源证明

使用固定manifest的稳定物理任务key。相同游戏/问题的重试、source replay、Spreadsheet同题变体不算新任务。一次实际尝试只登记一次；普通在线执行和隔离Train测试可记录不同`origin`，不要伪造成同一种Online成功。

不要求两个模型独立生成一份相同合同，不要求历史循环已经出现两次，不要求exact轨迹重放。程序可以走不同动作路径，只要通过实际检查。

### 7.3 测试调度与成本

一个新程序最多选择两个已获得的相关Train案例，各测试一次；可先测试一个、后续另一任务补足。同一候选的唯一修复版本沿用这两个已选对象，各至多再测试一次；新版本重新计数，不能继承旧版本的通过。优先复用自然在线调用结果；不因每个epoch重复遇到资产就重跑资格。

局部可检查时直接跑程序，不调用LLM。只能端到端判断时，后续Agent执行属于额外训练成本，必须记账。无法正确恢复前缀则从该Train题初始状态重新运行，不假装复原了中间状态。

测试例若被判为输入不适用，记`inapplicable`，不是成功也不是程序错误。禁止不断换题直到凑满两个通过；一次生成轮次的两个测试对象先固定。

### 7.4 失败处理

程序真实异常、输出缺关键字段或独立局部检查失败：当前episode停止重复调用该版本。仅Train写侧可按连续两个可归因失败将长期版本disabled。Val/Test只使用本题临时避用集合，不修改Frozen状态。终端任务答错但原因未知，不把所有参与过的程序一起删除。

`not_found/needs_input/blocked`是正常结果，不因为它们没有证明目标效果就强制回滚或永久禁用。搜索范围内未找到不意味着全局不存在。

## 8. Planner：从证明合同覆盖改为选择可执行策略

### 8.1 多步任务只做一个主要规划调用

输入：原始任务、少量相关Skill/Workflow接口、当前公开状态与工具。

输出：选中模板及参数，或一个短工作流。直接包含节点目标、程序/Skill引用、参数来源和必要顺序。取消常态下P1→P1R→P2→C1的多阶段证明式协议。

- 没有可用Bank时，直接用一个动态任务节点；不为冷启动先建立一套无法执行的形式图。
- 检索top8是提示词上限，不是隐藏工具权限；需要其他能力时通过普通检索工具获取，不重发整个Bank。
- 首次结构错误最多修复一次；修复仍无效则返回普通Dynamic任务，不中断Run。
- Stored Workflow只作为经验模板；不以“静态覆盖完整任务合同”决定是否有资格被考虑。

### 8.2 E2不再重放历史顺序

工作流Learner可以删除重复导航、把多处探索归为Find节点、复用既有Program、加入尚需Agent处理的动态节点。

代码只检查真实引用、普通类型、顺序/环和预算结构。不判定自然语言计划必然正确，不为Agent生成的边补造历史证明。新计划质量通过Train执行和正式held-out结果判断。

### 8.3 不再按历史同值推断DataFlow

必须由Agent明确指定 `from=node.field`。不要在后台用“source值刚好等于导航location”生成硬边。

Agent仍可能提出错误边；这种错误应在运行反馈后允许修订，而不是宣称边经过代码证明因此无法更改。保留原始任务和输出语义说明，有助于Agent分清“到达位置”和“在此找到目标”。

### 8.4 单轮QA例外是接口能力，不是benchmark私有策略

对于`single_answer`任务，不额外调用Planner做一次解题。检索现有指导/确定性处理后，正常solver只回答一次。程序处理不能藏一次LLM调用。该规则由Adapter能力声明控制。

## 9. Runtime：普通值传递＋局部反馈＋自动接续

### 9.1 节点输入

默认只发送：原任务必要限定语、节点目标、当前输入/缺失项、最新相关观察、少量可用调用、最近相关失败、简短搜索记录。完整状态与审计原文保留在磁盘；需要补充时提供句柄或按需读取。

不要使用要求模型展开`frame_rows/frame_map/frame_ref`的压缩语言；优先直接可读的短对象。不新增“总结Agent”。图像与文件窗口的正文预算在第二阶段按公开输入协议处理。

### 9.2 进入节点时

```text
解析参数引用
→ 程序usable且必要参数已具备：先执行程序
→ 无程序或缺参数：调用节点Agent
→ Agent进行一次原生操作、调用准备程序、补值或报告计划问题
→ 刷新公开状态
→ 再尝试当前已授权节点的程序
```

只要输入和公开条件允许，后续多个节点可连续执行，不逐节点向LLM重新请求同一调用。正常outputs只在status=ok且结构检查通过时发布；not_found/needs_input/blocked保留现场，但不把未完成节点当成功生产者。环境已经终止时按独立环境结果结束，不因worker来不及RETURN判整题失败。

多条ready路线按固定Train记录排序：已通过测试优先，再比较有效成功率、已观察成本，最后按ID确定性打破平局。不要因为没有唯一preferred证明就永远退回Agent。没有数据时保持明确的稳定顺序，不宣称最优。

### 9.3 绑定不再有多级“升为concrete”手续

程序和原生工具返回的普通结果进入本题ValueStore。实体ID或路径是否合法，在真正调用时由Adapter/broker检查。稳定对象ID不因每次revision变动就要求重新认证；位置等动态信息则使用新观察并处理实际拒绝。

用户要求、当前任务输入与计划猜测不能混在一起：保留原始goal；记录参数来自task/result/planner，便于冲突时修订计划。该来源是简短标签，不是新的证明系统。

### 9.4 计划冲突和修订

当前source/destination与公开反馈冲突时，允许一次任务级计划修订：改变尚未执行部分的参数、替换错误边或插入动态节点。已执行的真实动作不可删除；旧结果不可悄悄覆盖。重算尚未执行节点即可，必要时停止当前图并从真实当前状态进入Dynamic。

本题对象数量、用户目标等不得被“为了顺利执行”偷偷改掉。普通对象/文件引用保持精确；不做类别与实例模糊相等。

### 9.5 非执行诊断不制造任务失败

`detail`过长：保留raw，在展示记录中截断。无效status或实际执行字段错误仍拒绝；只有一次有界协议修复。没有有效调用且输出截断时保存原始失败，不无界追加长推理请求。

### 9.6 无进展与回滚

不使用revision增加作为唯一进展。相同调用/参数在相关状态未变化时重复拒绝两次，停止当前尝试并交给局部恢复/一次计划修订，不继续同样的昂贵循环。

- ALFWorld搜索未命中/普通动作拒绝：保留实际已走到的状态和公开历史，不自动prefix回滚重搜。
- 程序异常：不发布正常outputs，刷新实际环境再恢复；只在显式支持可靠恢复且确实需要重试时使用checkpoint。
- 文件修改：在隔离工作区中事务提交，失败丢弃未提交输出。
- 所有已发生动作、失败与费用仍记录；不得因恢复而抹掉成本。

## 15. 工厂、配置与Runner的精确接线

### 15.1 当前源码的实际限制

当前`load_config()`先调用`mechanism_profile.resolve()`，后者只接受legacy或mechanism.v2；所以新profile在进入System构造之前就被拒绝。包根`atomic_skillgraph/__init__.py`还会立即导入旧System。旧`train_dev16/deploy`直接使用旧`artifact_index`、`ManifestStore`、旧checkpoint、maintenance和freeze_manifest。

**不直接复用上述控制层。** 复用的是底层Provider、公开环境、任务清单与稳定的小型I/O函数。

### 15.2 固定入口

```python
# entrypoint/factory.py（可合并进empirical/system.py）
def create_system(config_source):
    raw = read_yaml_or_mapping(config_source)   # 只读取，不调用旧load_config
    if raw.get('mechanism_profile') == 'skillcompiler.empirical.v1':
        from atomic_skillgraph.empirical.system import EmpiricalSystem
        return EmpiricalSystem(validate_empirical_config(raw))
    from atomic_skillgraph.system import AtomicSkillGraphSystem
    return AtomicSkillGraphSystem(raw)
```

- `__init__.py`使用lazy import保留历史导出名；不在导入empirical时触发旧System导入。
- 新`run_empirical_pilot`与`run_multibench`使用此工厂；旧r103 runner保持legacy，不把新Bank伪装成旧database对象。
- 新配置必填：profile、实际模型配置、benchmark profile、manifest、run_seed、输出目录、train/frozen模式、既定预算。
- API认证检查仍保留：只允许环境变量名，不把密钥写进配置/快照。
- 不要求新配置补齐old condition、Repeat=4、P1R/P2R、old repair_revision等已废弃字段。

### 15.3 Runner公共返回值

`run_task()`返回一个普通EpisodeResult：run/task/attempt ID、split、sealed prediction或终态引用、raw score/hard/soft、终止原因、程序/原生调用日志路径、费用记录路径。Runner不再调用旧的contract_agreement或compiler-observation代码来决定是否完成。

最外层阶段：`task_started → task_execution_finished → learning_finished(仅Train) → task_committed`。训练任务即使答错也可完成并留下经验；infrastructure_failed与方法答错分开。

## 16. 普通I/O与自动接续的完整合同

### 16.1 统一结果字段

原生工具只使用一份结构：`accepted, observation, data, error, done`。Program使用`status, outputs, detail`；只有`status=ok`时按其output schema检查并发布outputs。`detail`不进入执行权限与成功评分。

- `not_found`：保留真实当前位置/已读取内容；不发成功输出、不自动回滚。
- `needs_input/blocked`：暂停当前节点，交给一次正常局部决策；不自动完成消费者。
- exception/timeout：不发布outputs；保留已发生的环境副作用、费用和错误。
- 环境done/won：由主进程终止整题，拒绝后续原生动作；worker未返回或返回异常不能覆盖真实终态评分。
- `ok`、`accepted`、官方成功是三个不同字段；不用节点自报成功写score。

### 16.2 ValueStore与计划修订

ValueStore只保存本题task公开值、Planner选择、节点返回值，来源标签用于调试，不构造证据链。参数只使用正文中的四种引用。

执行器串行执行拓扑序；进入节点、一次准备返回之后都尝试已授权的ready Program。缺字段才询问Agent；不要所有节点预先问一次Agent。普通动态节点可通过`complete_node(outputs)`结束，仍只做输出schema检查，不声明其语义已经证明。

修订只改未执行节点。需要重做已执行能力时插入新node_id，保留旧结果与日志；不能把旧outputs暗改成新值。修改前驱引用后，重新计算所有尚未执行消费者的参数缓存。结构环、不存在的node/field与执行能力的自然语言质量必须区分：前者代码检查，后者由执行反馈处理。

同程序+相同参数+相同相关状态已经失败，不在自动接续中立即无限重试；遵循原定两次无变化失败上限。选择和回退只用Train记录，Frozen期间不从Test分数更新全局排序。

## 17. Python worker、环境Owner与文件提交

### 17.1 固定生产实现，不留“普通进程也算沙箱”的解释空间

使用Linux/WSL2上的Docker兼容容器后端。优先rootless；容器非root用户、`--network=none`、`--read-only`、`--cap-drop=ALL`、`no-new-privileges`，限定memory/pids/cpu/tmp。镜像按digest锁定，禁止挂宿主根、模型密钥、答案目录和docker.sock。

Python `-I`、AST检查、删import、删builtins都**不算安全边界**。无容器时只能跑手写离线fixture，不能悄悄退回宿主exec运行模型代码。检查这项属于现有“真沙箱”要求，不是新语义证书。

### 17.2 JSON RPC与状态所有权

- 一个episode的环境由唯一host-side adapter/owner持有；Python Program不持有环境对象。
- worker通过stdin/stdout消息调用`observe/available_tools/remaining_calls/call`；print走stderr，父进程并行drain并限制长度，防止协议混杂或堵管道。
- broker将允许工具、task_scope、program_version、episode budget绑定在父进程；不能采用脚本自报的权限、分数或计数。
- 每次call使用(invocation_id, sequence)去重；同ID同参数返回已知结果，同ID异参数拒绝。
- `call(name,args)`每次在最新公开目录精确解析，不缓存旧action_id；脚本无需提供revision证明。
- 一个episode同一时刻只允许一个实际native call在途。worker超时先关闭租约，再终止worker；正在执行的原生调用必须收尾或终止其环境owner后，才允许恢复Agent继续。不能让旧调用在新决策后又改变环境。
- 无法确认原生操作是否完成时，该attempt标记状态未知并停止；不能盲目重试同一副作用操作。

### 17.3 时间与计数

维持v3预算：默认worker总wall=60秒，Spreadsheet=120秒；等待RPC也在wall内。每个native工具本身设不超过剩余deadline的执行超时。Python无RPC死循环同样可终止；不要求静态证明循环次数。

保留两种实际计数：`native_call_attempts`包含拒绝；`environment_steps`只在真实env.step时增加。32是单次Program的native调用尝试上限；ALFWorld整题100按实际环境步数，OfficeQA/Spreadsheet按既定原生工具次数。LLM、程序和恢复成本分别记录，不能把一次Program包装当一次环境动作。

### 17.4 文件任务必须在第一阶段有同一worker的工作区能力

不用再套第二个方法执行器。host从公开resource handle准备本次stage目录，容器只挂本题允许输入与stage，程序通过固定sandbox路径使用预装库。动态Python工具与持久Program用同一镜像、工作区和权限，区别仅在代码来自本次调用还是Bank。

程序内部不能再次递归启动`execute_python`，也不能安装包或读Evaluator。成功返回后host检查声明输出存在、在stage内部、非逃逸symlink，发布完整版本目录并原子切换manifest；失败丢弃未提交stage。输出文件的存在/可打开不等于Benchmark评分正确。

同一Program同时产生的真实环境动作不能随文件回滚一起抹掉；当前六个Adapter按stateful environment或workspace选择正确的恢复方式。

## 18. “两个Train案例”如何实际测试，不把旧证明问题搬回来

### 18.1 一个普通TrialCase足够

```text
case_id / physical_task_key
public_task_ref
start_mode: reset | prefix_replay
prefix: 原生name+args序列（可空）
inputs: 该案例起点可获得的普通参数
check: 独立local check ID，或task_outcome
continuation: 继续当前流程的runner配置（可空）
```

这些是运行测试用的数据，不让模型填写witness或owner。`physical_task_key`来自固定manifest而不是临时trace_id；Spreadsheet同题变体共享一个key。

### 18.2 起点必须真的存在

- 测试使用新建的独立Adapter/工作区，不使用已经terminal的训练harness原地restore。现有AlfWorldAdapter明确拒绝terminal restore。
- 优先选择程序能从reset直接运行的案例，如query+公开scope的搜索。
- 若测试取物/处理等中间能力，在独立实例上精确执行已记录prefix，直至测试起点；动作不可重放、提前terminal则该case不可建立，不伪装成复原成功。
- prefix重放使用真实当前目录，每个case的输入独立构造，不能把来源A的keychain_1/文件路径直接复制到来源B。
- 从旧Trace拷贝“执行后的事实”到当前环境或ValueStore，不能代替实际执行。新输入只能来自该次公开task、已执行prefix的公开结果或新的显式选择。

### 18.3 判断通过与继续学习

局部有可靠检查时，不需要LLM续跑。没有局部检查时，使用正常Agent接着完成Train任务，独立scorer检查最终结果；这些额外LLM调用记入trial阶段成本。

若候选失败后Agent重新执行同一局部能力、覆盖了候选输出，不给该候选正向记录。无需形式因果证明：记录candidate返回是否被消费、是否在局部恢复中被替代即可。即使整题通过，也只记录task_outcome依据，不包装为局部语义证明。

两个对象在看到其测试结果前固定；修复仍使用同一对case。修复次数最多一次；不同版本重新计数。暂时没有第二个适用Train来源就等待后续自然任务，不借Val/Test，不伪造第二来源，也不为凑结果无限挑题。

失败经验允许Learner提出假设，但不能把失败source本身登记为新程序实测成功。旧轨迹只提供材料，生成后的程序必须实际执行。

## 19. 持久化、冻结和恢复：最少事务，不能只写“支持resume”

### 19.1 内容与状态分开

Program的内容版本固定：源码、entry、I/O schema、允许工具、ABI、镜像digest。I/Workflow绑定具体版本。Trial行用attempt_id唯一键，附physical_task_key、版本、结果依据和origin；相同attempt重复写入幂等，内容矛盾则报错。

可以使用一个新的SQLite库加不可变程序文件目录；不需要旧EvidenceLedger或certificate闭包。导出Frozen只打包usable程序、仍可用的指导/Workflow和完整依赖。Workflow中缺usable程序的节点显式走dynamic，不要求整个工作流都已证明完整。

### 19.2 Train/Val/Test写边界

Train可以更新状态。Val/Test只读库，临时程序/plan/避用集合按task隔离；下一题不继承临时工具或Test观察。调用日志、费用写在run目录，不在Frozen数据库中更新use_count/disabled/ranking。Freeze前后hash稳定。

### 19.3 中断恢复

1. 已完成Episode且已提交学习事务：不重跑。
2. Episode结果已落盘但Learner未完成：从保存的公开经验继续学习；不重做环境交互。
3. Agent请求已收到并落盘，结果事务未提交：恢复已有响应并幂等提交；不能再生成一次不同候选。
4. native call有intent但无完成记录：状态未知，不声称exactly-once。停止当前attempt，按Adapter恢复能力重建或重新开始该题；保留全部已知成本，旧attempt不增加成功来源。
5. 收不到Provider计费信息时记录unknown，不把它写成0；没有可用调用ID就不能保证不被Provider重复计费。

不实现复杂分布式事务；单writer、任务级checkpoint、两个清晰提交点足够。恢复正确性只验证一次实际副作用和一次信用登记，不能承诺网络上真正exactly-once。

## 20. Provider与费用接入不能原样复制

当前`OpenAICompatibleProvider`只支持deepseek_v4_chat；消息content要求str，图像list会被拒绝；`UsageBucket`也不会接受任意新阶段字符串。它的HTTP/usage经验可以复用，不代表接口已经多模型、多模态兼容。

第一阶段：DeepSeek文本配置维持原样，费用可以映射现有bucket：planner→planner_p1，solver/runtime→runtime_dynamic，learner→extractor_e1，builder→tool_builder_evolution；用普通`phase`区分train/trial/val/test，不为stage名字再建证明系统。

第二阶段：Provider按已锁定endpoint和能力选择dialect。消息允许str或标准content parts；图像二进制/资源handle由Provider桥接真实发送，不先str()。DeepSeek的thinking字段、OpenAI兼容端点的reasoning字段、其他端点的SDK字段按实际能力转换；不把一个Provider的私有字段发给全部模型。

费用只采用实际response usage和HTTP记录。不支持的字段为null，reasoning若已含在completion中不再相加。程序无LLM；每次生成、修复、trial续跑和失败请求都计入整轮真实成本。

## 21. 本轮实际核验结果与未核验范围

交付包的`03_工程核验报告.md`、`checks/`和`probe/`提供可重跑结果：10项原源码叶模块探针、47项受控实现测试。当前text-only Provider、profile拒绝等是**已复现的现状限制**；测试通过不表示这些旧函数已经修好。

47项包括普通结果传递、多动作RPC、真实AlfWorldAdapter方法接入（backend是受控替身）、自动接续、参数修订、两任务实测计数、Frozen、未知副作用恢复、工作区发布等。程序均是手写fixture，不是学习产物，禁止导入正式空Bank。

原备份缺失`atomic_skillgraph/traces/`源码包，直接运行选定旧pytest在collection阶段失败；这不是仓库代码缺陷。测试通过namespace加载完整叶模块执行，未伪造缺失包，也未声称全量回归通过。

本环境没有Docker和真实ALFWorld/TextWorld数据，因此未验证生产OS隔离、真实游戏或模型自然生成。生产前需要的容器preflight与一次生成/Train测试仍是原第12节同一验收，不是新增实验矩阵。

## 22. 范围冻结与完成定义

**按本版实施，不再回到旧证明型主线，也不另外引入第三套方案。** 后续审查只核对第12节和15—20节列出的接口、错误路径、任务测试与实验隔离。已经明确删除的witness/owner/完整覆盖证明不重新作为放行条件。

三项结论分别登记：
- `implementation_ready`：生产接线、隔离、恢复、评分和数据链实际通过。
- `mechanism_demonstrated`：真实Train生成程序在正常路径多动作复用并可自动接续；手写fixture不满足这一项。
- `measured_effect`：同题成功、费用与动作数据如实报告；不预先保证降幅、不删除失败seed。

此前固定的有限验证完成后，逐benchmark开始正式矩阵，不追加“理想Bank全部实现/每题全自动/每类都学出固定工具”的门槛。若真实运行发现异常、泄漏或预算错误，必须修；不能用“永不再报问题”代替工程事实。普通效果波动不会自动触发新的架构重写。
